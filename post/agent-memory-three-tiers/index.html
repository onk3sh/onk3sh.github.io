The three-tier memory layer I built for my coding agent

Most agent memory designs either forget everything between sessions or accumulate noise until they're useless. Here's the architecture that avoided both.

The default Claude Code memory story is: write a CLAUDE.md, keep it updated, hope for the best. It works until it doesn't. The file gets stale, contradictions accumulate, the agent starts reasoning from outdated context and you don't notice until something goes wrong in a PR review.

I wanted something auditable. Three independent tiers, each with a different durability horizon, each audited by its own linter on a defined schedule. Here's what I built and why each tier exists.

The problem with single-tier memory

A single memory file has two failure modes that pull in opposite directions. If you prune aggressively, you lose context that would have prevented a mistake three weeks later. If you keep everything, the file grows until it's too long to be useful as context — the agent loads it, but the relevant entry is buried under a hundred stale observations.

The insight from Andrej Karpathy's LLM wiki pattern is that memory needs a garbage collection cycle, not just an append log. Entries should have a decay mechanism. Contradictions should be detected and resolved. The memory should be a curated knowledge base, not a journal.

That solves the noise problem. But it doesn't solve the durability problem — some things you want to remember for years (architectural decisions, domain knowledge), some for days (current task context, in-progress decisions), and some just for the session (scratch notes, intermediate reasoning). Putting all three in one file is the wrong abstraction.

Tier 1: LLM Wiki (session-to-session knowledge)

The LLM Wiki is the Karpathy pattern implemented: a curated markdown knowledge base in ~/.claude/ that the agent reads at session start. Entries follow a strict format — observation, evidence, confidence, last-validated date. No entry survives without evidence. No entry survives indefinitely without revalidation.

The weekly GC cycle is enforced by lint-memory, an auditor that runs independently of the agent. It checks for entries older than the TTL without a revalidation date, flags contradictions between entries, and removes observations that are now derivable from the codebase directly (the codebase is the source of truth; the wiki should only store what can't be read from code).

The result is a wiki that stays small. My current wiki is 47 entries covering the two production codebases I work in daily. It fits comfortably in a single context window. The agent reads it in full on every session start.

Tier 2: Obsidian vault (long-horizon knowledge)

The Obsidian vault is the second brain — architectural decisions, design rationale, meeting notes, things I want to remember across months, not sessions. The agent has read/write access to a dedicated Claude/ folder via the Obsidian CLI.

This tier exists because some context is genuinely long-lived and too detailed for the wiki. A decision about why a service uses eventual consistency instead of strong consistency — the reasoning, the alternatives considered, the tradeoffs accepted — is the kind of thing you want searchable six months later when someone asks why the design looks the way it does. The wiki would prune it. A flat file would bury it. Obsidian keeps it searchable.

The agent writes to the vault at the end of significant tasks — architectural decisions, non-obvious debugging paths, anything that would save future-me thirty minutes of reconstruction. It reads from the vault when context tags suggest a relevant note exists.

Tier 3: JSONL session knowledge graph (intra-session state)

The third tier is a JSONL knowledge graph that persists within and across a working session. It's not designed for long-term retention — it's designed to give the agent structured access to what it learned earlier in the same working context, without relying on the conversation window staying in scope.

The graph records entities and relationships: files modified, functions touched, design decisions made, blockers encountered and resolved. The agent queries it before starting a new subtask to check whether relevant context already exists. This eliminates a class of redundant re-investigation — the agent doesn't re-read files it already summarized, doesn't re-derive decisions it already made.

The session graph is audited by system-gc, which runs at session end and compacts entries that are now redundant (superseded by a later observation, or covered by a wiki entry that was updated). It also extracts durable observations and promotes them to the wiki with a confidence flag, so session learning flows upward into long-term memory when it should.

Three auditors, not one

Each tier has its own auditor: lint-memory for the wiki, lint-skills for the skill library, system-gc for the session graph. Running three independent auditors matters for a specific reason: a single auditor has no external reference. It can only check internal consistency. Three auditors can cross-check — lint-memory can flag wiki entries that contradict what lint-skills knows about a tool's actual behavior.

The auditors run on separate schedules. lint-memory runs weekly (the wiki changes slowly). system-gc runs at session end (the graph changes every session). lint-skills runs when a skill is updated (triggered by the PostToolUse hook on skill file writes).

What this looks like in practice

A typical session start: the agent loads the wiki (47 entries, full read), checks the session graph for in-progress context (usually empty at session start, populated on resume), and queries Obsidian if the task description references a known domain area. Total overhead: under 3K tokens on a cold session start. On a resume, the session graph provides the agent with a structured summary of where it left off — no re-reading of conversation history, no manual "here's what we were doing."

The thing that surprised me: the auditing discipline matters more than the architecture. A three-tier system without GC degrades to noise faster than a single-file system, because you have three places accumulating stale entries instead of one. The value of the design is the scheduled cleanup, not the structure itself.

What's missing

Two things I haven't solved. First: cross-session graph continuity. The session graph resets between disconnected sessions — if I close a task and come back a week later, the graph is cold even if the wiki has the relevant context. A persistent graph with TTL-based decay would fix this, but I haven't built it yet.

Second: confidence propagation. When the wiki is updated based on a session observation, the promoted entry gets a confidence flag, but that flag doesn't propagate if a later session contradicts it. The wiki can hold two conflicting entries at different confidence levels without surfacing the conflict to the agent at read time. lint-memory catches this on the weekly cycle, but not inline.
