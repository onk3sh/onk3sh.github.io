Iron-Law Gates: How I Turned My PR Review History Into an AI Pipeline

Most people building AI coding workflows optimize the model. Better prompts, bigger context windows, smarter agents, fresher benchmarks. That's the wrong variable.

The model is a commodity. The process around it isn't. Your AI pipeline will only stop the failures you have explicitly told it to stop — and the only reliable source of "what fails in your codebase" is your own review history.

So I went and got mine.

The audit

Over three months I worked through 100+ PR review comments across two production services I contribute to. I copied every non-trivial reviewer comment into a spreadsheet, tagged the underlying failure, and looked for repetition. I did not care about one-off stylistic preferences. I cared about the things that came back.

Sixteen categories survived the cut. They split cleanly by service.

A few things worth calling out. The two services have almost no overlap in failure modes. Service A's worst failures are concurrency and entity-state bugs — the things a strongly-typed, transactional, ORM-heavy stack punishes. Service B's worst failures are logic errors and duplication — the things a dynamic, two-language stack punishes. Same engineer. Different traps.

This is the entire point. A generic AI code reviewer cannot know that .some() vs .every() is the modal failure in this codebase, or that copy-constructor identity drift has shipped to production twice. My reviewers know. Their comments are the ground truth.

The insight: four intervention layers

Sixteen categories is too many gates to operate. But they cluster.

  1. Correctness — logic errors, concurrency, entity copy gaps, data shape, defensive overreach. Wrong code.
  2. Design — model design, controller bloat, duplicate logic, UI state misuse, dead code. Right answer, wrong shape.
  3. Scope — scope creep, intentionally-removed-feature re-add, dead code from prior refactors. Wrong boundary.
  4. Safety — migrations, feature flags, test quality. Wrong blast radius if it ships.

Each layer fails at a different point in the development arc, which means each layer needs a different gate. Catching scope creep at code review is too late — the work is done. Catching a concurrency bug at planning is too early — there's no code to reason about yet.

The pipeline: disciplined-development

Five phases, each non-skippable, all built on Claude Code. The discipline is the product. The model is incidental.

Phase 1 — Requirements (dd-scout)

Fetches the ticket, parent epic, sibling tickets, all comments, and any linked specs or ADRs. Produces a structured requirements brief: in-scope, out-of-scope, open questions, acceptance criteria, related decisions.

Gate: blocks on any UNKNOWN. You cannot proceed to Phase 2 with unresolved questions.

This kills scope creep before it has a surface to grow on. The "intentionally-removed feature accidentally re-added" failure was the one that taught me Phase 1 needed to exist — the only way to not re-add a removed feature is to know, in writing, that it was removed.

Phase 2 — Plan

Implementation plan with four required sections: reuse inventory (what already exists), data-flow mapping (where state enters, transforms, lands), NOT-DO list (things a reasonable engineer might do that this ticket excludes), and Intentionally Removed Items (features deleted in prior tickets that must not return).

User-approved before any code is touched. The reuse inventory is the direct response to four "you duplicated this utility" comments. The NOT-DO list is the direct response to scope creep.

Phase 2.5 — Stress-test (grill-me / grill-with-docs)

Sequential design interview. One question at a time. Adversarial probing of the plan. Auto-routes to grill-with-docs — which pulls the relevant ADRs and internal docs into context — when Phase 1 surfaced sensitive paths: auth, migrations, payments.

This is where migration-safety and feature-flag failures get caught. The questions write themselves once you know what's been broken before: "What data assumption are you making about column X? How did you validate it? What's the partial-index scope and what happens to rows outside it?"

Phase 3 — Implement

TDD enforced. Per-file dedup check: any time two or more files would contain the same logic, the pipeline extracts a shared module before continuing. This runs because four reviewers, four times, said the same thing.

Phase 4 — Self-review

Thirteen ordered checks executed by four parallel sub-agents. Findings classified:

  • AUTO — fix immediately, no confirmation needed
  • BATCH — collect, fix together, single confirmation
  • MANUAL — surface to me with context, I decide

Results saved to Obsidian before Phase 5 is allowed to begin. The check list is the audit table, one-to-one. Every gate has a reviewer comment behind it.

Phase 5 — Completion

Evidence-required. Not "tests pass" — the actual command output, captured. Not "lint is clean" — the linter's stdout. dd-reviewer runs a full 13-check pass against the diff and returns go/no-go. Only then does the PR open.

[dd-reviewer] 13/13 checks complete
  correctness: pass
  design:      pass
  scope:       pass (NOT-DO list honored)
  safety:      pass (feature flag registered, migration validated)
  -> GO

The supporting stack

Briefly, because it's not the point — the gates are the point.

  • ast-grep + LSP for code search. ~70% token reduction versus grep on the same questions, because structural queries return structural answers.
  • difft for structural diffs that sub-agents can actually read.
  • shellcheck as a PostToolUse hard guard on Bash — the agent cannot run a shell command that shellcheck rejects.
  • Claude Code sandbox mode for execution boundaries. Filesystem and network allowlists.
  • Slack async observability so long-running phases don't require babysitting a terminal.
  • Custom Bitbucket MCP server, because no official one existed.
  • Three-tier memory: LLM Wiki (Karpathy's pattern) for durable facts, Obsidian vault for project state, JSONL session knowledge graph for in-flight context.
  • Three auditors: lint-memory, lint-skills, system-gc — they run against ~/.claude/ and flag drift.

All of this lives in ~/.claude/. None of it touches company code.

Honest assessment

Roughly 10 of my own tickets have gone through the full pipeline end-to-end. Separately, I've used dd-reviewer against 30+ external open-source PRs as a learning loop — running the 13 checks against code I didn't write, to see whether the gates fire on real failures or just on mine.

The gaps, plainly:

  • N = 10 is a pilot. It's enough to know the gates fire correctly on the failures they were built for. It is not enough to claim a defect-rate reduction. I'm not going to claim one.
  • Single-user. Every calibration decision was mine. A second engineer would tune the AUTO/BATCH/MANUAL thresholds differently.
  • Ceremony versus throughput. Five phases with hard gates is slower than just writing code for a one-line CSS fix. I skip the pipeline for trivial tickets. That's a feature, not a bug — but it means this isn't a universal answer.
  • The audit is a snapshot. Three months, two services, one engineer. Reviewer composition changes. Codebases evolve. I'll re-run the audit next quarter.

I'm not claiming this makes Claude Code "better." It makes my use of Claude Code reliably catch the failures my reviewers have flagged. That's a smaller, more defensible claim, and it's the one I'm willing to defend.

The methodology

Forget my pipeline. The transferable thing is the method.

  1. Pull your last 90 days of PR review comments. All of them. Not just the BLOCKERs.
  2. Tag the underlying failure, not the surface comment. "You forgot @Transactional" and "this isn't atomic across the batch" are the same failure.
  3. Count. Anything with three or more instances is a pattern. Anything with one is a preference.
  4. Cluster into intervention layers. Where in the development arc does each pattern first become catchable?
  5. Build a gate per layer, not per pattern. Sixteen gates is unworkable. Four or five is operable.
  6. Make the gates non-skippable. A gate you can skip when you're tired is not a gate.

The output won't look like mine. Your reviewers catch different things. Your stack has different traps. That's the point — a pipeline built on someone else's review history is just another generic tool.

Audit your own review history. Build gates against what you actually ship wrong. The model will keep getting better on its own; the process won't.
